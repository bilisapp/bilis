# Ingest

## Log ingest never returns 4xx for bad payloads
Ingest endpoints (routes/api.php: POST /api/v1/logs OTLP JSON, POST /api/v1/ingest simple JSON) are best-effort: malformed records are skipped and counted, never 400. Mappers return a MappedLogs value object (rows + rejected + errorMessage); controllers turn that into OTLP `partialSuccess` (200, `{}` on full success) or `{accepted, skipped}` (202). Any ClickHouseException — overload or not — becomes 503 with `Retry-After: 5`; never blame the client for storage failures.

DateTime64(9) values are built as strings by App\Services\Ingest\LogTimestamp (`Y-m-d H:i:s` + 9 fraction digits) so nanosecond precision survives; never round-trip nanos through a float or DateTime. ProjectId always comes from AuthenticateProjectApiKey::project($request), never the payload (SCHEMA.md R2) — it is a String column, so controllers pass `(string) $project->id` and the mappers take `string $projectId`.

## Mapped rows carry every otel_logs column explicitly
The insert names its columns, so a mapper row must contain all of them, in schema order, with an empty default where the payload has nothing: Timestamp, TraceId, SpanId, TraceFlags, SeverityText, SeverityNumber, ServiceName, Body, ResourceSchemaUrl, ResourceAttributes, ScopeSchemaUrl, ScopeName, ScopeVersion, ScopeAttributes, LogAttributes, EventName, ProjectId (SCHEMA.md R1).

OTLP mapping: `resourceLogs[].schemaUrl` -> ResourceSchemaUrl, `scopeLogs[].schemaUrl` -> ScopeSchemaUrl, `scope.attributes` -> ScopeAttributes, `logRecord.eventName` -> EventName. The simple format has no equivalents, so those are `''`/`[]` (EventName may come from an `event` field). There is **no ObservedTimestamp column** (R6): the observed time is still parsed, but only as the fallback for a record with no event time.

Trace flags come from `flags` — the proto field name, and what OTLP/JSON and the protobuf decoder both send. `traceFlags`/`trace_flags` are accepted as aliases for hand-written payloads only; do not "fix" the mapper by dropping `flags`.

## Protobuf OTLP is decoded here, in PHP, behind a flag
`application/x-protobuf` on POST /api/v1/logs is decoded by App\Services\Ingest\Protobuf — a hand-written wire-format reader (`ProtobufReader`) plus one method per OTLP message (`OtlpProtobufDecoder`). No composer package, no ext-protobuf; keep it that way. The decoder's only job is to emit **the same array shape `json_decode` gives for the OTLP/JSON encoding** (camelCase keys, nanos as digit strings, hex trace/span ids, base64 `bytesValue`), so OtlpLogMapper stays encoding-agnostic — `tests/Unit/Ingest/OtlpProtobufDecoderTest` asserts the two produce identical rows against fixtures generated by a real Go exporter (`tests/Fixtures/otlp/main.go` regenerates them).

`config('bilis.ingest.otlp_protobuf')` (`BILIS_OTLP_PROTOBUF`) turns it off, restoring the 415 with the JSON hint. Unknown fields must be skipped, never rejected; a body that will not decode is a rejected payload (200 + partialSuccess), not a 400. OTLP over gRPC remains unsupported.

Two hardening rules the parser must keep, both covered by tests:
- **Submessages are windows, not copies.** `ProtobufReader::readMessage()` returns a child reader over the shared buffer; decode methods take a `ProtobufReader`, not a `string`. Only leaf scalars (`readLengthDelimited`) copy. Reintroducing a `new ProtobufReader(substr(...))` per level brings back the depth×body memory blow-up (15 MB of adversarial nesting → ~800 MB) that a `substr`-copying reader had.
- **Every protobuf `string` that becomes a JSON string goes through `OtlpProtobufDecoder::utf8()`.** Wire strings are raw bytes, not guaranteed UTF-8; an ill-formed one reaches `ClickHouseClient::encodeRows` (`json_encode` with `JSON_THROW_ON_ERROR`) and throws, which surfaces as a 503 that fails the whole batch and loops the exporter. Scrub, do not reject — the JSON endpoint never hits this because `json_decode` rejects bad UTF-8 at the door. Byte fields (`bytesValue` base64, trace/span id hex) are already valid and are not scrubbed.

## Compressed request bodies are inflated in the application
Nothing in front of it does: not Traefik, not FrankenPHP — and the Collector's otlphttp exporter gzips by default, so before App\Services\Ingest\RequestBody a compressed export was acked and silently dropped. gzip/x-gzip/deflate/identity are inflated (capped by `bilis.ingest.max_decompressed_bytes`; a body that reaches the cap is discarded whole, never half-parsed); zstd/snappy/lz4/br answer 415 naming what is supported, because retrying cannot fix them.

## Map columns must serialize as JSON objects

Empty PHP arrays encode as `[]`, but ClickHouse JSONEachRow requires `{}` for
Map columns — and with `wait_for_async_insert=0` the server acks first and
discards the unparseable row silently. `LogWriter::write()` normalises the
three Map columns (`ResourceAttributes`, `ScopeAttributes`, `LogAttributes`)
to `stdClass` when empty; any new Map column must be added to
`LogWriter::MAP_COLUMNS`. Regression test: "empty attribute maps are
serialized as JSON objects" in `SimpleLogIngestTest`.

## Reading the ingest throttle's counters back
`ThrottleRequests::handleRequestUsingNamedLimiter()` does not hand the limiter's bucket to `RateLimiter` as written: it stores the counter under `md5($limiterName.$limit->key)` (`$shouldHashKeys` is true by default). So the dashboard reads `RateLimiter::attempts(md5('ingest'.'ingest:key:'.$keyHash))` — `IngestRateUsage::counterKey()`/`bucketForKeyHash()`. AppServiceProvider builds the same bucket through those helpers so the two can never drift; get it wrong and the panel silently reports 0 forever instead of failing. `ProjectApiKey::key_hash` *is* the sha256 the limiter buckets on, so usage is readable without the plaintext key. Covered by tests/Feature/Ingest/IngestRateUsageTest.php, which posts through the real throttle stack.
